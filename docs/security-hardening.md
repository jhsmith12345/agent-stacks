# Protected agent: implementation and remaining gates

This follow-up implements the local remediation work from the November 4 audit. It does **not** certify production security. The on-chain v5 bytecode and cryptographic construction are unchanged. The SDK remains a low-level trusted-RPC library; the protected executable is `examples/chain-agent.js` with `src/solana/trusted-agent.js`.

## Trust model and share release

The operator selects a validating node using an owner-only `AGENT_STACKS_TRUST_POLICY` file at process launch. A policy explicitly names the expected genesis, program, artifact length/hash, test-only scope, allowed features, and spending limits. Initialization messages cannot replace that node. A separate optional `submitRpc` can deliver transactions, but is never consulted for state, fee estimates or confirmations. Node provenance is an operator assertion: a URL, HTTPS certificate or policy file does not prove consensus validation. Protect the endpoint and its bootstrap/snapshot configuration; do not label a public provider operator-controlled.

The agent reads finalized state from that trusted node. It checks executable ownership, ProgramData PDA/metadata, exact artifact bytes and zero-only allocation padding. A retained upgrade authority is refused unless explicitly permitted for testing. The code check itself is only as trustworthy as the configured node. The supplied test-validator reports the System Program address in its authority field even with the CLI `none` option; tests deliberately use the explicit exception rather than treating that as a `None` authority.

Before returning a game view, the guard durably records slot, version, hand, state hash, registered keys and final-deck hash. It rejects earlier slots/versions/hands, different bytes at the same version, changed registered keys, changed accepted decks, and skipped-hand recovery. Both shuffle phases may legitimately change the deck; the first post-shuffle view pins the final deck. The trusted validator, rather than a new JavaScript replay engine, establishes that intervening transitions are valid.

Before computing `x*A`, the guard requires an unchanged accepted view, an obligation belonging to this seat, a valid non-burn position/cursor, the registered hand key, and an unexpired chain deadline. Own hole cards may be released only in the appropriate showdown phase. The exact release decision is fsynced first. Persistence failure stops the guard. This gate covers both strict and cooperative shuffle modes.

**This is a trusted-validator backend, not a Solana light client.** A malicious configured state node can fabricate an entire first view or a plausible later showdown. Pinning the deck cannot authenticate those obligations by itself. The regression suite intentionally retains that exploit under `compromised-trusted-node`. A dishonest submission relay is separately tested and cannot substitute game state. Supporting arbitrary untrusted state providers still requires a reviewed chain-authentication mechanism; comparing two RPC responses is insufficient.

## Signing, limits and recovery

The existing child process keeps wallet/hand keys away from the demo coordinator's messages. It accepts a small local IPC command set, serializes requests, limits the queue to eight and bounds message size. The chain strategy remains fixed check/call. No remote network control service or LLM plugin sandbox is provided. Guard and signing code share the same process: arbitrary code execution there or under the same OS user remains a compromise.

Buffer cleanup closes only accounts the program owns. Closed buffer addresses are public and anyone can fund one, so a funded system-owned address is ignored, and a failed refund is deferred rather than treated as fatal. An address funded before its buffer exists cannot be created, so the agent moves to a fresh key and keeps the old one on disk. Before signing, the guard checks transaction program IDs, match destinations, this wallet as buffer authority and payout-claim destination, fee payer, bounded compute limits, policy-approved priority fees, test-only rent transfers, account-rent limits and estimated fees. A payout to any other destination is a deliberate operator action outside the agent. Accepted matches must also fit the policy's clock ceiling (`maxTurnSeconds`, 24 hours if unset) and blind limits, because a long clock lets an opponent tie up funds for a long time. Co-signing an opponent's deck spends none of this budget, so repeated offers cannot stop an agent from signing its own moves; each match version accepts one deck and at most five signatures. Cumulative authorization count, fees and gross outflow are reserved durably **per match**. Any attempt whose bytes were released conservatively consumes budget, including failed and expired ones, and refunded rent does not reduce gross outflow. A transaction rejected in simulation was never released, so its reservation is returned; otherwise retrying one proof-account creation would use up the outflow limit. At the default policy limits, only about two released-but-expired proof-account creations can be absorbed before the outflow limit stops the agent.

Priority fees are off unless a policy sets `maxComputeUnitPrice` (`--max-compute-unit-price` in `scripts/trust-policy.js`). When enabled, the price is the 75th percentile of recent fees on the accounts a transaction write-locks, capped by that ceiling and by what fits under `maxFeePerTransaction` at the transaction's compute limit, and the fee counts toward all fee budgets. A failed estimate sends without a fee rather than blocking the action. Proof upload chunks shrink from 1,000 to 960 bytes to leave room for the fee instructions. These are not wallet-wide daily limits across operator-created policies/matches. The policy defaults allow two low-stake test hands and enough rent/transactions for strict fallback.

Every transaction is first simulated against the trusted node. A rejection there means its bytes were never released, so it is reported without recording anything; this covers cases such as an empty fee balance. A transaction that passes is recorded as pending, durably and before transmission, together with its `lastValidBlockHeight` and original signed bytes. Confirmations come from the trusted node and must be finalized, except proof upload, seal and verification-round steps (tags 9–11), which clear at `confirmed`. Those steps move no value and reveal no secret, are bound to an on-chain offset or round, resume from chain progress, and are re-checked on-chain when tag 13 consumes the proof, which still waits for finality.

A network error or crash blocks further signing until the pending transaction resolves, and the agent resolves it itself: it redelivers the original bytes (through the relay and directly to the trusted node) and clears the record on a finalized receipt, or once finalized block height has passed `lastValidBlockHeight` with no receipt. A transaction past that height can never land. Height is read before status so a landing cannot be missed, and this depends on the node retaining transaction history for that window. If a node without that history reported a false expiry, it still could not apply anything twice: every instruction the agent signs is bound to the match version, an upload offset or a verification round, and test transfers keep their own `transferOnce` marker. A pending record with no stored expiry height is never presumed dead and remains a manual reconciliation. Recovery never re-signs, never sends a replacement and never resets budgets.

The standalone agent retries what can safely be tried again, backing off up to 60 seconds and starting over whenever a transaction lands: RPC failures (every call is time-limited to 30 seconds), transactions rejected in simulation or left uncertain, an expired blockhash and an unfunded join. Each attempt re-reads state and re-runs every guard check, so retrying releases nothing. A match that is not yet visible at finalized commitment is also retried at startup, for up to two minutes. A changed program, rolled-back state, changed keys or deck, a budget breach, a persistence failure and any other unrecognized error still stop the agent immediately. The demo coordinator does not retry; use `--resume`.

Before joining, the agent requires its deposit, one proof buffer's rent and fees for the full-proof fallback on every hand, and otherwise refuses without depositing, joining by itself once funded. A refused co-signature forces that fallback, so it has to be affordable before a stake is committed. A creator cannot be gated this way, so it gets a startup warning instead. Policies with test controls skip this check because the demo coordinator lends these funds.

`scripts/reconcile-agent.js` remains read-only by default: `--apply` clears a finalized success/failure or a proven expiry, and `--rebroadcast` redelivers only the original bytes. Existing demo funding/rent-return markers still require separate reconciliation; do not delete them to retry.

```sh
AGENT_STACKS_TRUST_POLICY=POLICY_FILE node scripts/reconcile-agent.js \
  MATCH_MANIFEST PRIVATE_DIRECTORY PLAYER_PUBLIC_KEY
# After inspecting the finalized receipt, add --apply to record it locally.
```

Stop the signer before recovery. After a hard crash, verify that its recorded PID is dead before removing a stale lock. Do not restore an old checkpoint/backup and automatically resume: reconcile chain history, pending transfers and budget consumption first. Protection against malicious filesystem rollback requires a separate trusted storage/monotonicity boundary and is not implemented.

## Backups and secret handling

`scripts/backup-private.js` encrypts/decrypts an operator-prepared private archive using AES-256-GCM and scrypt (N=131072, r=8, p=1; backups written earlier at N=32768 still open), fresh 16-byte salt and 12-byte nonce, authenticated header, fixed format and a 64 MiB limit. The passphrase enters on descriptor 3; it is never an argument or environment variable. Output is exclusive and owner-only. Tests cover tampering, wrong passwords, truncation and randomized encryption.

```sh
node scripts/backup-private.js encrypt PRIVATE_ARCHIVE ENCRYPTED_BACKUP 3< PASSPHRASE_FILE
node scripts/backup-private.js decrypt ENCRYPTED_BACKUP NEW_PRIVATE_ARCHIVE 3< PASSPHRASE_FILE
```

Use a strong independently stored passphrase (at least 16 UTF-8 bytes), restrict its file to mode 0600, and protect trailing-newline conventions: the tool uses the exact descriptor bytes. Prepare a consistent archive while agents are stopped; include the wallet, active hand keys/proofs, guard checkpoint, accepted manifest, node policy and original transaction journals. Test restoration into an isolated directory. No live wallet backup or encryption migration was performed because no operator recovery passphrase was supplied. Live keys remain owner-only plaintext; JavaScript memory/BigInt are not a secure enclave. Best-effort Buffer clearing is not comprehensive secret zeroization. Secure old-key destruction, OS isolation and wallet-wide spending controls remain production work.

## Release tools

- `npm run check`: every test plus Rust formatting and Clippy.
- `npm run tools:verify`: compares the local Solana tools tarball with `solana-tools.sha256`, the official Agave v4.4.0 release digest.
- `npm run security:test`: focused adversarial client, recovery and storage tests.
- `npm run devnet:preflight`: read-only checks to run on each machine before a match: RPC behaviour and rate limits, program pin, funding at current rent, and the terms being accepted. It prints no URL or key.
- `npm run security:attest`: read-only code/authority check against the pinned node policy.
- `npm run security:reproduce`: two clean temporary source/target builds with cargo-build-sbf 4.5.0/platform-tools v1.57; compare both hashes to the workspace artifact. This checks same-host reproducibility, not independent supply-chain attestation.
- `npm run security:bundle -- .agent-stacks/review/NEW_DIRECTORY`: explicit allowlist of public sources, tests, docs, dependency locks, SBF artifact and named public validation receipts, plus a SHA-256 manifest and outstanding gates. Private caches, journals, ledgers and wallets are excluded.

The protected agent only accepts `network: test-only`; the existing network guard still refuses other public clusters. There is no production-enable switch in this work.

## Required before a real-stake release

1. Independent cryptographic analysis and independent Solana/client review of the complete frozen package; address findings and obtain regression review. See [the reviewer brief](external-audit-brief.md).
2. Separate-host devnet runs using operator-controlled nodes, including strict fallback, missing funds, stale/unavailable nodes, crash recovery, deadline races and cost measurements. The [two-machine runbook](devnet-two-machines.md) has the procedure and the drills. A run through a hosted RPC labelled `--third-party-rpc` measures timing only and does not satisfy this gate.
3. Review OS-level signer isolation, encrypted live-key custody, retention/backup restoration, wallet-wide spending policy and monitoring. A withholding relay is now routed around by redelivering the original bytes directly to the trusted node; this is tested locally, not on a public network.
4. Review measured fallback duration and fee/rent reserves under load. The guard refuses clocks below one hour and the demo defaults to 24 hours; neither is a public-network availability guarantee. A strict shuffle through the real agent measured 406 seconds on a local validator at 400 ms slots, about 11% of a one-hour clock, including a restart mid-upload. Through a proxy injecting RPC failures at about 1.8% of requests, the slowest shuffle took 1,160 seconds, about 32% of the clock. The low-cost demo has run on public devnet, taking 462 seconds against 114 locally. Full-proof timing on a public network is unmeasured, including under congestion with priority fees. The on-chain program still permits 30-second clocks, which the strict path cannot meet, so correct behavior depends on this policy until a later program version separates the shuffle clock. The full proof still needs about 4.54 test SOL temporary rent per buffer and hundreds of transactions.
5. Freeze the release, reproduce it on an independent host, verify deployed bytes and deliberately remove upgrade authority only for an audited production version. Future versions get new program IDs and fresh player opt-in. A multisig/timelock changes the trust model; it is not equivalent to immutable custody. No public authority was revoked here.
6. Choose the binary format and build environment before freezing, because each changes the pinned hash. The build depends on the host: a Mac build and two fresh Linux CI builds have different hashes, with the same size and the same instructions once addresses are masked, but the functions in a different order. Gate 5 therefore needs one agreed environment, such as a pinned Linux container. The pinned artifact is SBPFv0, and `SIMD-0500` would stop new deployments of v0, v1 and v2 programs once activated. It was inactive on devnet and mainnet on 2026-11-05. A scratch SBPFv3 build of the same source passed all 19 Rust tests and deployed on a validator using devnet's feature set. Its binary is 6% smaller and it used less compute at three of the four measured steps; the fourth, a DLEQ check, rose by 3 units to 16,932. Make both changes together, before the audit.

An incident response starts by stopping new matches/signatures and preserving private journals. Check the trusted node, balances, final state and original pending signatures; keep fee reserves for legitimate completion/claims. Do not expose keys or “repair” a private-state mismatch by deleting caches. An immutable program cannot be patched in place, so deployment must wait for the review gates above.
